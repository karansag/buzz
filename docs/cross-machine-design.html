agent-swarm · design, implemented on master 2026-09-28

Hub and Nodes

One agent-swarm server stays the source of truth. Every other machine runs a thin tmux daemon that dials in over the tailnet. Same commands, same handles, one dashboard. Reviewed by the hoopoe agent at every step; its corrections are marked. Where the code went its own way: the node's session fence is a local object rather than the hub's generation number, a spawned pane carries the server that created it from the creation command, a node token may only touch agents on its own machine, and task notifications from agents go out in the agent's name. Not built: the owner login for reverse-proxy dashboards and the task importer.

What breaks today

agent-swarm is single-machine in every layer, and the assumption is load-bearing:

  • The server binds loopback and identifies an agent by its tmux pane id, such as %12, plus the local tmux server id. Both mean something only on the host running that tmux.
  • /send resolves the sender from the caller's pane. A CLI on another machine has no way to say who it is.
  • Delivery, the activity monitor, peek, spawn, stop, and pane titles all shell out to the local tmux binary.
  • Image attachments are delivered as an absolute path on the server's disk, which a pane elsewhere cannot open.
  • The dashboard, task board, and teams read one SQLite file.

The goal: agents in tmux panes on several machines register, message each other, share one task board and team structure, and appear on one dashboard, with the same commands and the same [agent-msg from ...] contract they use now.

What master already has

  • Pane ids and tmux server ids replaced positions this week. That is the right local half of a cross-machine address.
  • A host name is sent with every registration but only used to build the handle. It is not stored. It becomes the node column.
  • Image attachments landed, delivered as hub-local paths. Decision 6 answers that.
  • The in-session model picker was removed, so there is no keystroke choreography left to move across the wire.

Prerequisite: bare handles

Agreed with hoopoe. Auto-assigned handles currently append harness, model line, and host, as in hoopoe-codex-gpt5-karanslinux. All three are mutable or better kept as columns, and the host is stored nowhere else. Hoopoe's own handle says gpt5 while it runs GPT-6.

  • Handles come from the pool bare; a numeric suffix only when the pool is exhausted. The 48-character requested-name limit stays so existing long handles remain legal.
  • The reported host is persisted as node and shown next to flavor and model in recipients, the protocol brief, and the dashboard card. It is never inferred from an old suffix.
  • The tag builder, model line parser, host tag, and the tag parameter on name picking are deleted.
  • No automatic renaming. Existing handles stay. Re-registering with --name is an explicit rename that rewrites message and task references. While suffixed handles exist, foo-anything reserves bare foo.
  • Existing rows get the hub's node name as a one-time local-data migration, justified by their local tmux ownership, not by parsing a suffix.

Decision 1Topology

chosen

One hub, thin nodes. The server keeps handles, messages, tasks, teams, monitor state, and the dashboard. Every other machine runs buzz-node, a small daemon from the same package that drives its local tmux and nothing else. The hub's own tmux is served in-process through the same interface. Run the hub on the machine that stays on; here that is karans-linux.

Hub drives remote tmux over SSH. No daemon on nodes. The first draft overstated the case against it: SSH can invoke one remote helper that does paste, delay, submit, and verify locally, so four round trips per delivery are not inherent. It is not chosen because continuous monitoring, reconnect, spawn, and capability reporting all want a long-lived process, and it needs hub-to-node SSH keys next to the Tailscale identity that already exists. Because the hub reaches nodes through one interface, an SSH node can be added later.

Federated servers, one per machine. Tasks, teams, queens, and dependency graphs live in one file, and the value of the tool is that the owner sees one board. Federation either replicates that state or elects one authoritative server, which is this design with more parts. Hoopoe agreed there is no case for it at this scope.

Decision 2Connection direction

chosen

One outbound WebSocket from node to hub. Commands go down with an operation id and a deadline; results come back tagged with the id; observations stream up on the same socket. The socket is the heartbeat. Nodes never listen and never publish a callback address, auth is enforced only on the hub, and a laptop behind a network that blocks inbound connections still works.

changed in review

The first draft had the node run an HTTP listener that the hub called, with an announce-and-heartbeat dance to learn its address. Hoopoe preferred the socket: it removes the second listener, the second auth surface, and the callback bookkeeping, and gives one channel for everything. Cost accepted: the hub keeps per-node connection state and needs the protocol below.

The socket protocol the implementation must specify:

  • Every command carries an op id, kind, absolute deadline on the hub clock, and arguments. A command whose deadline has passed when dequeued is dropped, so a laptop waking from sleep never executes an old paste.
  • Every result carries the op id and one of ok, failed with a reason, or unknown, meaning the node cannot say whether the side effect happened.
  • Bounded queues both ways. A full queue fails the oldest command as unknown rather than blocking.
  • Hello on connect: node name, protocol version, package version, tmux server id, harness binaries available.
  • Heartbeat with a timeout in both directions; reconnect with backoff on the node.
  • Connection generations. A new connection fences the old one, and results arriving on a fenced connection are discarded. On reconnect the hub re-snapshots the node's panes before marking its agents available.
  • A connected socket does not mean tmux is healthy. Every observation batch carries the tmux server id; a node whose tmux is gone says so and its agents read offline.
  • Mutating operations on one pane are serialized on the node, so a paste and a kill cannot interleave.

Decision 3Monitoring placement

chosen

Node captures and streams; hub classifies. The node captures its registered panes on the hub's interval and sends observation batches up the socket: pane id, exists, foreground command, title, capture hash and text when changed, a sequence number, and the tmux server id. A batch goes every tick even when nothing changed, which is the liveness signal. The hub runs the activity classifier exactly as today. On reconnect the hub discards old observations and resets stale timers.

Run the classifier on the node and push only status changes. Rejected for v1. The classifier changed this week; keeping it in one process avoids version and reset semantics across two, and the traffic saved is unmeasured. Revisit with measurements.

Decision 4Addressing

An agent's address is node, pane id, and tmux server id. The node name is AGENT_SWARM_NODE or the short hostname, sent by the CLI on register and send and stored on the recipient. Handles stay global and server-assigned from the one pool, so puffin means the same agent from every machine. A requested handle is a hub-wide claim: first registration wins regardless of node, and a later request for a taken, live handle gets a 409 naming the owning node.

added in review

Every pane operation carries the expected tmux server id, and the node checks it at execution time. Checking only at the hub allows a tmux restart between observation and delivery to target a reused pane id. Positional targets are resolved on the node named in the request, never against the hub's tmux, and the pane migration runs per node against that node's own snapshot. Every legacy row is hub-local by construction, so the migration's clock-based heuristic never has to compare clocks across machines. One tmux socket per node in v1.

Schema: recipients gain node, and uniqueness becomes node plus pane id plus server id. Tasks gain a worktree node. Message delivery becomes a three-way status. A nodes table records name, token hash, last seen, version, tmux server, harnesses, and connection generation.

Decision 5Auth

Today there is no auth and the server binds loopback. Once the hub listens on the tailnet, anyone who reaches it can type into every registered pane on every machine, so the deferred tailnet-auth item stops being deferrable.

chosen

Per-node bearer tokens bound to node identity. buzz node-token <name> on the hub creates or rotates a token, prints it once, and stores a hash. The node daemon and the CLI on that machine send it. The hub derives the node from the token and rejects a register or send whose claimed node differs, so one node cannot impersonate another. Revoking a laptop is deleting its row. Owner operations are authorized separately; a node token cannot act as the owner.

changed in review

Hoopoe found a contradiction in the first draft, which let announce overwrite an address while a second machine with the same name got a 409. Identity is now the token, not the name: the same token reconnecting fences the previous connection; a different token claiming an enrolled name is refused. It also caught that binding only the Tailscale IP drops the loopback listener the local dashboard uses, and that a reverse proxy makes remote requests look local.

  • Listeners. The hub listens on loopback and its Tailscale IP. Binding all interfaces is acceptable only because every non-loopback request requires a token.
  • Loopback trust. Tokenless loopback requests are trusted by default so the local dashboard keeps working. When tailscale serve or any proxy fronts the hub, the operator turns that trust off and the dashboard authenticates.
  • Browser login. A login page posts an owner token and sets an HttpOnly, SameSite=Strict cookie. No token in a query string. Mutating dashboard requests check Origin.

One shared token. Less to manage, but every laptop holds the hub's entire authority and a lost one means rotating every machine. Tailscale identity headers or tsnet. Not needed for v1 on a single-user tailnet; revisit if the tool ever serves more than one person.

Decision 6Attachments

chosen

Structured attachment ids, rendered on the recipient node. A deliver command carries the text and a list of attachment ids; the hub does not format paths into the text. The node fetches each id it lacks from the hub's authenticated attachments endpoint, validates type, size, and content hash, writes atomically into its own cache, and only then renders the attached-image lines and pastes. A failed fetch means delivery has not started. The node keeps a file for at least the hub's retention window after last delivery, so an agent that opens the path minutes later still finds it.

A shared filesystem or rsync. Rejected because it adds a setup step outside agent-swarm and breaks silently when missing.

Decision 7Spawn and repositories

Spawn takes a node and a structured request: harness, model, autonomy, and a working directory. The node validates the binary and directory before launching and returns a useful error otherwise. Available harnesses come from the node's hello, so the dashboard offers only what that node has.

changed in review

The first draft said a worktree's node can be read off the assignee. Reassignment or an agent moving nodes breaks that while the files stay put. Tasks now persist the worktree as node plus path, set from the updating agent's node. The queen prompt gains one sentence: a worker must push its branch and report the remote ref and commit when marking a task done, and the integrating agent fetches it. A local path alone is not a handoff.

Decision 8Delivery semantics

review's top finding

Today the hub records a message after the tmux paste returns, in one process, so the window in which a message is delivered but unrecorded is microseconds. Across a network that window becomes ordinary: a node can paste and submit successfully and the result can be lost. That outcome is unknown, not failed, and replaying it would submit the message twice.

  • The hub records the message as pending before dispatch, and the message id is the command's op id.
  • The node keeps a bounded, durable record of recently executed mutating op ids. A repeated id returns the recorded result instead of running again.
  • Message status is delivered, failed, or unknown. Unknown shows on the dashboard with a resend control for the owner. The hub never replays an unknown mutation on its own. Read-only operations retry freely.
  • Exactly-once is not promised. A crash between the tmux side effect and recording its result stays ambiguous, and the design says so.
  • Unreachable and confirmed absent are distinct. The node reports that a pane is gone; the hub infers nothing from a dropped connection. Prune cannot delete a registration because of a network failure.
  • Dispatch handles failure immediately. Missed heartbeats set the dashboard's node status; a send to an agent on a node with no live socket fails at once.

The node daemon

On start it connects to the hub with its token, sends hello, then loops: execute commands from the socket, stream observations on the interval.

CommandArgumentsNotes
panespane id, label, command, title for every pane, plus tmux server id

capturepane, tmux_serverdashboard peek

The hub side is a Node protocol with two implementations: a local one that calls the tmux module directly and always returns ok or failed, and a remote one that wraps a socket connection and can return unknown. A registry on app state maps names to nodes. Calling the server edits mechanical was optimistic, as hoopoe noted: results gain the unknown state, messages are recorded before dispatch rather than after, and every operation carries a server id. Expect a behavior-level pass over send, owner send, task notification, spawn, stop, prune, and the monitor tick.

Per-machine setup

The CLI and the node daemon read one per-machine config file, written once:

buzz join http://karans-linux:8765 --token <from: buzz node-token karans-macbook-pro>
# writes ~/.agent-swarm/node.toml: hub url, token, node name (short hostname unless --node)

Environment variables override the file when set, and the loopback default applies when neither exists, so a single-machine install needs no file. A file rather than shell-profile exports because an agent already running in a tmux pane inherited its environment at launch and cannot pick up new exports; its harness runs the register command as a subprocess, which reads the file. That is what makes migration a re-register rather than a restart. The bundled register skills work unchanged.

Migrating existing machines

Two kinds of machine exist today, and the hub cannot tell which from outside because a local server binds loopback.

Agents in tmux, no server of its own. Nothing to migrate. Install the package, run buzz join, start the node daemon, and have each agent register with the hub. Each gets a handle from the hub pool.

A machine running its own agent-swarm server. It has its own handles, messages, tasks, teams, and attachments. Its agents were registered by a stable agent id the hub has never seen, so re-registration creates a fresh hub row with no clash, and registering twice returns the same hub handle. The old database is archived, not merged:

  1. On the hub, once the naming prerequisite and the first two implementation steps are deployed: buzz node-token karans-macbook-pro.
  2. On the machine: pull, reinstall, stop its server, rename its database to db.sqlite.pre-hub, run buzz join with the token, start buzz-node as a launchd or systemd user service.
  3. Ask each live agent to register. It keeps running in its pane; the CLI reads the new config file. An agent that wants its old handle asks for it with --name; the hub grants it when free and refuses it when a live hub agent holds it, in which case the agent takes the assigned one. The protocol brief lists its peers under their hub handles.
  4. Open tasks are the one thing worth carrying over. buzz import-tasks db.sqlite.pre-hub --node karans-macbook-pro creates them on the hub with new ids, keeps title, description, status, worktree with its node, and dependencies, and sets the assignee only when an agent has re-registered under the same handle. Task numbers inside old message text are not rewritten; they refer to the archive.
  5. Teams are few; re-create them on the dashboard. Message history and closed tasks stay in the archive, readable any time by pointing a scratch server at it.

Rollback on that machine is stopping the node daemon, restoring the archived database, and starting its old server; nothing in the archive was modified. Why not merge the databases: handle, task id, and team id collisions would each need rewriting across messages and task references, and the text of old messages cannot be rewritten reliably. The live board is what matters, and open tasks carry it.

Failure behaviour

SituationBehaviour
Node down or laptop asleepSocket drops; disconnected at once for dispatch, after the heartbeat timeout for the dashboard. Sends fail immediately with the node reason and are recorded. On reconnect the hub re-snapshots panes, then agents return with the same handles.
Hub downNothing works anywhere. Same as today; run the hub on the always-on box.
Hub restartsNodes reconnect with backoff. Commands in flight at that moment are unknown.
tmux restarts on a nodeNew server id in the next batch; rows bound to the old one read offline until re-registration. Commands carrying the old id are refused by the node.

Implementation plan

Each step leaves the single-machine path working and the tests green.

  1. Bare handles and the node column. Prerequisite, one commit. Delete the handle tag code, persist node, migrate existing rows to the hub node, show it in recipients, protocol brief, and dashboard card.
  2. Node interface and delivery semantics, local only. Protocol, local node, registry, nodes table, worktree node, three-way message status, record-before-dispatch. Route every tmux call through the registry. Tests cover the unknown path.
  3. Node daemon and socket transport. The daemon, the socket protocol with op ids, deadlines, fencing, hello, heartbeat, and observation batches; the remote node; per-node tokens with claim validation; attachment fetch with dedup. Tested in-process with tmux monkeypatched, including deadline expiry, duplicate op ids, and reconnect fencing.
  4. Dashboard. Node names, node strip, spawn node select and cwd, unknown-message marker and resend, login page and loopback trust switch.
  5. Docs. A "Multiple machines" README section, agent prompt note that peers may be elsewhere and paths are per node, upgrading entry, roadmap item closed.

Rough size: about 600 lines for the daemon and interface together, a 250-line server diff, 100 across db and client, 150 in the web app. Four focused sessions; the socket protocol and its tests are the bulk.

  • Paste an image into the remote agent's chat; confirm the path is on the MacBook and the agent can open it.
  • Kill the node daemon mid-delivery; confirm the message shows unknown, is not replayed on reconnect, and resend works once.
  • Sleep the MacBook with a send queued: the dashboard shows the node disconnected and the send has failed. Wake it: the queued command is expired, not executed, and the agent returns with the same handle.
  • Restart tmux on the MacBook; confirm its agents read offline with the stale-server reason and a delivery carrying the old server id is refused.
  • Spawn a Codex agent on the remote node into a chosen directory and stop it.
